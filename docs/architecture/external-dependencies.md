# External Dependency Policy

## 目标

这个文档用来约束“我们如何接第三方依赖”，避免只在正常路径上开发，等到线上限流、超时、空响应或格式变化时才暴露问题。

## 依赖分级

### 1. 强依赖、权威源

例子：
- `Gate`、`Binance`、`OKX` 的交易所价格

特点：
- 业务上就是要看这个源，不能被别的源替代
- 不要求再找一个“同类备用源”

要求：
- 必须有超时、错误状态、日志、前端可见的健康状态
- 必须定义降级行为：
  - 失败时本轮跳过
  - 使用上一次缓存
  - 或仅影响部分功能，但不能让整个服务失控
- 测试必须覆盖至少一个 failure path

### 2. 可替换的参考源

例子：
- 外汇参考价

特点：
- 业务需要的是“这类参考数据”，不是某一家供应商本身

要求：
- 默认不应长期单点依赖一个第三方源
- 至少要有以下之一：
  - 主源 + 备用源
  - 主源 + 本地缓存 + 明确失效策略
  - 明确文档化的例外说明
- 测试必须覆盖：
  - 主源成功
  - 主源失败后的降级路径

当前实现：
- 主源：`open.er-api`
- 备用源：`HexaRate`
- 两个源都失败时，服务回退到数据库里的最近一条 `USDCNY` 缓存值，并把 Forex 服务状态标记为 `Error`

### 3. 非核心依赖

例子：
- 邮件通知
- 统计、埋点、可观测性上报

要求：
- 失败时不能阻断核心监控流程
- 必须 fail-open，最多降级为“告警没发出去”，而不是“主流程停掉”

## Failure Path 怎么测

“failure path” 不是等线上真的坏了再测，而是在测试里主动制造失败条件。

常见方式：

- 用 `httptest.Server` 返回 `429`
- 用 `httptest.Server` 返回 `500`
- 返回非 JSON 或字段缺失
- 返回空结果
- 在 handler 里 `time.Sleep`，配合更短的 client timeout，制造超时
- 用 `context.WithTimeout` 制造 deadline exceeded
- 用自定义 `RoundTripper` 直接返回网络错误

## 对外部依赖的最小测试要求

任何新增或修改的外部依赖，至少要有：

1. happy path
   - 第三方返回正常数据时，系统能正确解析并使用

2. failure path
   - 至少一种失败情况：
     - timeout
     - `429`
     - `5xx`
     - 非法响应
     - 空数据

3. 降级验证
   - 失败后系统是否按预期退化：
     - 标记状态为 `Error`
     - 使用缓存
     - 跳过本轮
     - 不阻断核心流程

## 上线前检查

如果本次改动涉及第三方依赖：

- 除了本地单测，还要做一次真实依赖请求验证
- 如果依赖是核心路径，要确认：
  - 当前线上网络可访问
  - 当前返回结构和代码假设一致

## 文档要求

新增第三方依赖时，要在这里补充：

- 它属于哪一类依赖
- 失败时的系统行为
- 当前测试覆盖了哪些 happy path / failure path
